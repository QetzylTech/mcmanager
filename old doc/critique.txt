This is the most important remaining engineering risk.

* PID reuse protection
* stdout/stderr capture

* Windows Job Objects

I agree with that decision.

### There is also one particularly important Windows issue

The design recognizes the problem:

> POSIX worlds survive manager death; Windows Job Objects with `KILL_ON_JOB_CLOSE` do not.

It then says the Windows configuration must disable that behavior when worlds need to survive manager restarts. 

That's reasonable, but I'd make one decision explicit:

**World survival across manager restart should be a cross-platform invariant, not a deployment option, unless you intentionally want different semantics by OS.**

If the product requirement is "manager restart must not stop Minecraft servers," then the Windows implementation should default to that behavior too.

Otherwise you have:

Linux:

`Manager dies → Minecraft survives`

Windows:

`Manager dies → maybe Minecraft dies`

That's an undesirable product-level semantic difference.

# 3. Minecraft readiness is still under-specified

This is one of the biggest Minecraft-specific gaps I found.

Document 15 has:

> C8 readiness via socket

and the architecture correctly says a log line must not be the sole source of truth. 

But **a listening Minecraft TCP port is not equivalent to "Minecraft is ready."**

A server can bind its port before the world is fully usable.

You need a hierarchy of readiness signals.

I would define something like:

1. Process exists.
2. Minecraft server port is listening.
3. RCON is accepting connections, if enabled.
4. A safe readiness probe succeeds.
5. Server reports an operationally valid state.
6. Only then transition `starting → running`.

For supported versions/server types, the readiness adapter should be capable of choosing the best available signal.

This matters especially with:

* large worlds
* Forge/Fabric/Paper startup
* datapack loading
* plugin/mod initialization
* world generation
* slow disks
* Java GC/startup delays

The current architecture recognizes this generally, but the exact **readiness contract** isn't sufficiently Minecraft-specific.

The official Minecraft setup documentation confirms that server startup is fundamentally a Java process and that `eula.txt` and `server.properties` are created/used during initialization. ([Minecraft.net][1])

# 4. EULA handling needs an explicit product rule

This is a real omission.

Minecraft's official setup flow explicitly requires the operator to set:

`eula=false → eula=true`

before the server can run normally. ([Minecraft.net][2])

Your design has:

* world creation
* templates
* setup
* protected configuration
* server.properties editing

but I did not find an equally explicit **EULA acceptance model**.

The manager should not silently flip `eula=true` as part of provisioning.

I'd add:

* `eula.txt` is recognized as a protected Minecraft-required file.
* The manager detects whether EULA acceptance exists.
* First launch of an unaccepted server enters a clear `EULA_REQUIRED`/setup state.
* The UI presents the EULA acceptance requirement.
* Only an explicit operator action records acceptance.
* The manager writes `eula=true` only as the result of that action.
* Acceptance is audited.
* The manager never implies that it is granting the license itself.

This is small, but it is exactly the kind of Minecraft-specific behavior that belongs in the design.

# 5. `server.properties` needs version-aware semantics

The design correctly says that `server.properties` should be guarded and validated.

But Minecraft server properties are **version-dependent**.

This is particularly important now because Mojang has been moving properties into game rules and adding/removing properties across versions. For example, Minecraft Java 1.21.9 removed several old properties in favor of game rules and added management-server properties. ([Minecraft.net][3])

Therefore, this:

> "approved keys and approved value formats"

isn't enough.

The configuration model should distinguish:

**Core manager-owned properties**

Examples conceptually:

* server port
* RCON configuration
* IP binding
* query settings if supported

from:

**Version/server-type-dependent properties**

Examples:

* properties that exist only on particular Minecraft versions
* Paper-specific properties
* Forge/Fabric-specific behavior
* deprecated properties
* properties replaced by gamerules

The validator should be driven by a **server-type/version capability schema**, not one universal hard-coded list.

Otherwise upgrading a world from one Minecraft version to another can cause the manager to reject legitimate settings or preserve obsolete ones.

---

# 6. Java compatibility needs to become a first-class compatibility matrix

You already model `JavaRuntime`, which is good.

But the design currently treats:

> Minecraft version + server type + Java runtime

as configurable attributes.

That's not quite enough.

These combinations have compatibility constraints.

For example, current Paper documentation lists substantially different Java requirements across Minecraft versions, including Java 21 for 1.20–1.21.11 and Java 25 for 26.1+. ([PaperMC Docs][4])

Therefore the template/runtime model should be able to express:

`Minecraft/server type/version → supported Java major versions`

and preferably:

`recommended Java version`

plus:

`minimum Java version`.

The manager should validate the combination before starting.

Otherwise an administrator can select:

> Minecraft X + Java Y

and only discover incompatibility after launching.

Your architecture is already designed for this; the missing part is the compatibility contract.

# 7. Backup correctness needs more Minecraft-specific detail

The current backup sequence is conceptually correct:

> pause autosave → flush/save → capture → resume autosave

and the requirements explicitly call for coordination with the server. 

But this needs to be nailed down more precisely.

You need explicit semantics for:

* what command is used to flush saves
* how save completion is detected
* what happens if RCON becomes unavailable
* what happens if the server crashes while saving
* what happens if `save-off` succeeds but `save-all` fails
* what happens if the manager crashes after disabling autosave
* how `save-on` is restored
* whether backup is allowed while the server is unreachable through RCON
* whether offline worlds can simply be copied
* what files are included/excluded
* how symlinks/reparse points are handled
* what happens when a mod/plugin writes outside the expected world directory

The current documents give the **workflow**, but not all of these operational edge conditions.

This is probably the largest Minecraft-specific area that deserves one more design pass.

# 8. Backup format is still a design decision

You say:

> zip or snapshot

That is not actually one implementation.

For a manager that may handle very large worlds, the backup engine needs a defined strategy.

You should decide whether the first implementation is:

* ZIP
* tar-based archive
* filesystem snapshot where available
* copy-to-staging + archive
* content-addressed/deduplicated storage
* another format

And specify:

* compression
* checksum algorithm
* atomic completion
* temporary-file naming
* interrupted backup cleanup
* verification after creation
* restore validation
* artifact corruption detection

The checksum field exists, which is good, but the **backup artifact integrity protocol** isn't fully locked.

# 9. Restore has one potentially serious edge case

Your restore flow is:

> validate → stop → pre-backup → stage → archive → switch → restart if previously running.

That's a good architecture.

But there needs to be a clearly defined state if the final switch succeeds and the restart fails.

For example:

`old world archived`
→ `new world installed`
→ `Minecraft fails to start`

What exactly happens?

Does the manager:

1. leave the restored world in place and mark `error`?
2. automatically roll back?
3. attempt rollback only after a failed readiness check?
4. restore the old world automatically?
5. require an operator?

The domain model supports rollback/recovery concepts, but the **decision tree for failed post-restore startup** should be explicit.

You don't want this decision invented inside `RestoreService`.

# 10. Security is conceptually strong, but I would tighten several implementation requirements

The security model is much better now than the original design.

It has:

* server-side auth
* server-side authorization
* sessions
* CSRF
* step-up authentication
* password hashing
* secret isolation
* audit snapshots
* throttling
* immutable security records

That's solid.

OWASP's current guidance is consistent with several of these choices: opaque unpredictable server-side session IDs, `HttpOnly`, `Secure`, appropriate `SameSite`, server-side session state, and avoiding browser storage for authentication tokens. ([OWASP Cheat Sheet Series][5])

But I would explicitly lock these:

### Password hashing

Say **Argon2id** rather than merely "modern algorithm."

OWASP currently recommends Argon2id as the preferred password hashing choice. ([OWASP Cheat Sheet Series][6])

### Session rotation

Explicitly require session ID rotation after:

* login
* privilege elevation
* password change
* step-up authentication if applicable

### Cookie security

You already have:

* HttpOnly
* SameSite=Lax
* Secure over TLS

Good.

But I'd explicitly define whether HTTPS is mandatory for non-loopback deployment.

### Security headers

I don't see a sufficiently explicit security-header contract.

At minimum I'd specify:

* Content-Security-Policy
* X-Content-Type-Options
* Referrer-Policy
* frame-ancestors / clickjacking protection
* appropriate cache control for authenticated/private content

### Password reset/recovery

I don't see a complete account recovery model.

If there is intentionally **no password-reset mechanism**, say so explicitly.

Otherwise it becomes an implementation-time invention.

# 11. Secrets in SQLite are acceptable for this project, but encryption-at-rest is still unresolved

The design deliberately puts secrets into SQLite rather than `.env`, which is internally coherent.

But:

> stored server-side

isn't the same as:

> encrypted at rest.

OWASP recommends centralized, protected secret handling and emphasizes limiting exposure, rotation and preventing plaintext leakage. ([OWASP Cheat Sheet Series][7])

You should decide whether the `secrets` table stores:

**A. encrypted secret material**

or

**B. plaintext secret material protected solely by filesystem/DB permissions.**

For a Minecraft manager, I strongly prefer A.

Otherwise someone who obtains a copy of the manager database can potentially obtain:

* RCON credentials
* sync credentials
* other secrets

The design should specify the encryption/key-management model before production.

This is not necessarily a blocker for starting development, but it is a blocker for calling the security design finished.

# 12. SQLite concurrency is good enough for the stated scale, but the write model needs careful implementation

Your use of SQLite is reasonable for a single-host manager.

The documents correctly recognize that Operations and AuditRecords are high-write tables and that the deployment isn't internet-scale. 

But you should explicitly specify:

* WAL mode
* busy timeout
* transaction boundaries
* read/write connection behavior
* checkpoint policy
* handling `SQLITE_BUSY`
* long-running backup/cleanup transactions
* whether database backups use SQLite's backup API versus copying the `.db` file

That last point is particularly important because you have ManagerBackup.

**Do not simply copy the SQLite file while it is being written and call that a database backup.**

Use SQLite's backup mechanism or a transactionally safe equivalent.

This is an implementation detail that should be elevated into the ManagerBackup contract.

I would classify the current design as:

**~90–95% architecturally complete.**

Not because there are huge missing subsystems. There aren't.

Readiness, EULA, RCON, save coordination, server.properties/version capabilities, Java compatibility.
