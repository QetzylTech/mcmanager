CURRENT REALIGNMENT ADDENDUM — 2026-11-07
========================================

This addendum supersedes the assessment and proposed action list below. The
older plan's observations are preserved as historical rationale, not current
findings. Its `core/` and `core/STATUS.md` assumptions, recommendation to keep
the application under core/, and earlier blanket missing-feature findings are
stale: the repository's application is now at root `app/`, and
docs/IMPLEMENTATION_STATUS.md (last verified 2026-11-07) and
docs/WORKBOARD.md record the current verification snapshot. The latest
implementation added durable lifecycle-operation dispatch and expanded the
administration, catalog, configuration, history, and world-management APIs.
Some previously identified gaps have since been implemented; others remain
partial as recorded below. Numbered Documents 4–14 remain the product
contract; this file and the gate pseudocode do not override them.

Current tree and contract
------------------------

The live application package is `app/`; migrations are at root `migrations/`,
with tests and benchmarks at root `tests/` and `benchmarks/`. Important current
paths:

  app/bootstrap.py, app/__init__.py
  app/domain/{entities,lifecycle,invariants,events,deletion_tiers,value_objects,tuning}.py
  app/ports/{persistence,process_control,minecraft,filesystem,backup_engine,

                notifications,diagnostics,save_coordination}.py
  app/commands/world.py; app/web/{middleware.py,errors.py,api/,streams/};
  app/shell/{routes.py,templates/,static/}

There is no current `core/` application package. Do not move or recreate one.
Document 12 remains normative for target structure and dependency direction.
Actual placement differs in places: shell templates/static are within
`app/shell/` rather than root `templates/` and `static/`, and services still

to Document 12. `app/commands/` and the API/stream catalog are only partial;
the single `app/commands/world.py` does not mean the full command/query layer
or route catalog is complete.

Reconciled gate status
----------------------

All five gates remain partial; the focused implementation below is not full
product completion or a release pass.

Gate 1 — Process/Minecraft adapters. Implemented: ProcessControlPort and
POSIX/Windows adapters; argv launches and PID-identity guards; Minecraft
capability/readiness/EULA/property/Java adapter pieces; bounded log buffers,
VERBOSE_LOGGING filtering and durable session logs; fake-server C1–C14 tests.
The fake flags are `--crash-after-ms` and `--save-slow-ms`. Windows conformance
passed in the recorded run; POSIX has not been run. The service and HTTP EULA
acceptance flow exist (`WorldsService.accept_eula`,
`app/web/api/system.py`) and audit explicit acceptance; the route still does
not implement Document 10's ConfigEdit Operation/202 contract. Remaining:
cross-OS acceptance and full Doc 14/Doc 10 conformance. Documents 13–14 govern;
the gate1 sample's PID dataclass, seconds-based flags and universal readiness
threshold do not.

Gate 2 — Persistence/domain/auth/configuration. Implemented: Documents 6–7
domain types and initial migrations, FK enforcement/checking, Argon2id via the
encrypted secrets store, session hashing/step-up foundations, three-tier
effective settings and versioned ConfigEdit Operations. Selected user, role,
and permission administration routes are also implemented. The schema is the
Document 7 model, not gate2's simplified SQL sketch. Remaining product
coverage includes complete authorization/grant-management and schema/migration
release verification. Focused Gate 2 tests passed per the recorded status;
this does not certify every Doc 6/7 invariant.

Gate 3 — Control plane. Implemented: derived world-lock query; durable queued
lifecycle operations with idempotent replay, atomic dispatch, and recovery
after container rebuild; progress and terminal audit/notification integration;
conflict policy; scheduler missed-run recording; startup reconciliation;
supervisor and scheduler workers started by `create_app`. `RuntimeService` is
presently a facade and `WorldsService` still owns lifecycle logic. Documents
6–9 govern conflict and state behavior; do not use the old generic pseudocode
rules.

Gate 4 — Operational subsystems. Implemented: native ZIP/SHA-256 backup,
storage/save guards, off-only restore with pre-backup and compensating rollback,
backup-artifact cleanup with preview/floors/blast-radius guard, and separate
sync with recorded retries/cap. Cleanup is currently backup-artifact scope;
stale-world/log cleanup and the Document 10 backup/restore/cleanup/sync API
workflows remain incomplete. Sync is not coupled to local backup validity.
Documents 6–9 and 14 govern the details.

Gate 5 — API/streams/shell. Implemented foundation: session/auth/CSRF/step-up
middleware; administration, schedules/templates/Java-runtime catalogs,
configuration, history, and world-management APIs; durable operation reads
and lifecycle enqueue routes; authenticated SSE snapshots and replay;
BroadcastChannel leader/follower client; and no-reload navigation. The
backup/restore/cleanup/sync API workflows remain unimplemented. Manager
backup/restore/restart/update/rollback routes are registered but return
`NOT_IMPLEMENTED` pending a manager lifecycle service. The complete Document
10 contract, all Document 4/5 workflows, operation cancellation, command
layer, stream deployment evidence, and calibrated Doc 11 performance release
gate remain incomplete. Do not claim the old sample's route/security semantics
or benchmark numbers are current.

   by this documentation task.

   `benchmarks/thresholds.json` must not be filled with invented values.

   current feature foundations.

  SyncService records write-once attempt timelines, makes three total
  attempts with 30/60-second waits, enforces the 50 GiB daily cap, and has a
  mounted-NAS transport.
  It is dispatched separately from local backup creation, so network failures
  do not block or invalidate the local artifact.

5.1 HTTP API / CSRF (gate5 Module 1)

Implemented:
  GET  /
  GET  /pages/<slug>
  GET  /api/pages, /api/pages/<slug>
  GET  /api/health, /api/diagnostics, /api/system/stats
  GET  /api/session
  POST /api/auth/login|logout|step-up
  GET  /api/worlds, /api/worlds/<id>
  GET  /api/operations/<op_id>
  POST /api/worlds/<id>/start|stop|kill
  POST /api/supervisor/tick
  GET  /stream/events, /stream/worlds/<id>/events|logs
  GET  /stream/restore_logs, /stream/metrics

Middleware enforces a SameSite session cookie, CSRF cookie/header equality on
POST/PATCH/DELETE, administrator role checks on privileged world mutations,
the AuthenticationService step-up window for stop/kill, and security headers.
Except for public shell/static/health/login paths, API reads and all SSE
routes require a live session. The login/step-up endpoints rotate the session
cookie; the CSRF cookie is readable by the browser for the double-submit
header and derived from the opaque session token, so arbitrary equal tokens
and tokens copied across sessions are rejected.

The lifecycle routes dispatch through the commands layer and return 202
operation envelopes; GET /api/operations/<op_id> reads persisted state.
However, the existing WorldsService lifecycle methods still execute through
their service call before the HTTP response. A durable background dispatcher
is still needed for truly prompt asynchronous acceptance and idempotency
handling.

Not implemented: remaining Doc 10 catalog (world creation/update/delete,
EULA/runtime-config, backup/restore/cleanup, settings/schedules, templates,
java-runtimes, admin, notifications/audit/files/logs, sync, and setup).

5.2 BroadcastChannel SSE (gate5 Module 2)

Implemented: shell/static/stream_client.js elects one same-origin tab over
BroadcastChannel("mcmanager_stream_channel"), opens /stream/events in the
leader, fans events out to followers, sends heartbeats, and re-elects after
leader departure. SSE routes now subscribe to RealtimeHub, deliver a snapshot,
replay after Last-Event-ID, fan out live events, and release subscribers when
the response closes.

Remaining: browser-driven server integration with authenticated sessions and
long-running reconnect/replay behavior is not yet a release E2E suite.

5.3 Persistent shell (gate5 Module 3)

Implemented: the 17-slug shell intercepts navigation, fetches page fragments,
updates browser history, and keeps a 40px shared button geometry, existing
shared color tokens, and no inline style overrides.

Remaining: page modules still render scaffold content; world selection,
context switching, functional workflows, and the complete Doc 4 component
system are not implemented.

5.4 Tests / performance (gate5 Module 4)

Gate 5 acceptance/browser tests cover CSRF, session/step-up, operation
envelopes/reads, SSE replay/fan-out, 17-module in-place navigation, and
10-tab leader failover. Existing Gate 3/4 lifecycle and composition changes
remain intact.

The checked-in thresholds.json is still a 1-second CPU/traced-memory smoke
file. Doc 11 requires a measured reference host profile, a 300-second idle
window, RSS, 50-client/1Hz stream fan-out, and 1000-lines/sec log ingestion
with a documented tail-latency limit. Those calibrated values/profile are not
available here; do not claim a performance release pass or fabricate them.
The current acceptance contract also calls the same manager stream both
anonymous-rejected and anonymous-open; keep the stream authenticated and
resolve that test expectation before claiming the full suite green.
